# 五分钟项目演示稿

我用这个演示介绍模拟电商客服项目。代码、评测和材料包含 Codex 辅助，独立编码能力需另外评估。以下是约五分钟的讲解安排，尚未录制或测量真实演示时长。

## 演示前准备

在项目根目录运行 `docker compose --profile monitoring up -d --no-build --wait --wait-timeout 60`，访问 `/ready` 确认数据库、FAQ、模型就绪。预先打开三个页面：

- [Swagger 问答](http://127.0.0.1:8000/docs)
- [Grafana 仪表盘](http://127.0.0.1:3000/d/rag-stage4)
- [本轮实测报告](career-evidence-report.md)

屏幕只展示问题、响应、报告和脱敏日志。不要打开 `.env` 或显示展开后的 Compose 配置。真实生成需要已经配置的 DeepSeek 服务，发生超时时展示实际降级返回及历史原始证据，不声称本次演示成功。

## 0:00–0:35：问题与范围

“这是一个模拟电商客服项目。我想解决两个不同的问题：查询某一笔订单或退款时，要根据记录回答；询问一般店铺政策时，要根据文档证据回答。系统还需要知道什么时候不能可靠回答，转为提示用户联系人工。

这里的订单、退款、店铺规则都是模拟数据，没有接入真实商家，也没有真实人工工单系统。项目采用 AI 辅助开发，我可以按代码和实测证据解释实现与限制，独立能力需要另外验收。”

## 0:35–1:15：两条链路

“FastAPI 收到请求后先做输入校验和分流。个人查询缺单号会追问，有单号就读取模拟订单或退款记录。一般政策走另一条链路：把问题转为本地 BGE 向量，在 PostgreSQL 的 pgvector 中取前三条 FAQ，再交给 DeepSeek 组织回答。

每条 FAQ 带规则 ID、文件行号和版本。生成结果要符合 JSON 结构，而且引用 ID 必须来自这次检索。证据不足或依赖故障会返回人工提示；引用合法并不自动保证每句话都正确，所以还要逐题评估。”

## 1:15–2:15：展示三种真实返回

在 Swagger 的 `POST /ask` 中依次执行以下输入。每次说明实际结果，不能只说 HTTP 200。

```json
{"question":"我的订单发货了吗？","order_id":"ORD-1001"}
```

“这条返回 `order_lookup`，依据模拟订单记录回答已发货；它没有用店铺一般发货期限猜测个人状态。”

```json
{"question":"付款后一般多久发货？"}
```

“这条应返回 `faq_rag`，引用 `RULE-SHIPPING-01`，保留工作日及预售的条件。我会核对实际输出，不能因有引用就跳过事实检查。”

```json
{"question":"广州线下门店的具体地址是什么？"}
```

“文档没有门店地址，应返回 `handoff`、空引用和 `needs_human=true`。这代表系统正常拒绝无依据回答，不是已经替用户创建了人工工单。”

## 2:15–3:20：实测与错题

打开本轮报告和 `docs/evidence/20261003-career-run/raw.json`，读取报告当前的准确数字，不背旧数据。

“我保留了固定题集、每题期望、实际答案、检索排名和请求编号。原基线是 44/46 自动检查通过，错题暴露了两个路由问题：‘我想了解发货规则’被误当个人查询，两个单号同时传入时退款被订单分支抢占。我调整判断后，原固定集自动检查达到 46/46。

自动检查涉及 HTTP、字段、路由、人工标志和引用；它不是整体语义准确率。逐题复核还发现过‘店铺核实’或‘审核通过’条件省略，所以报告单独记录语义问题，没有把所有答案包装成完美。

性能测试分别运行重复问题和新问法、并发 1 和 2，原始响应和耗时都保留。这里只报告本轮样本结果，不把短测吞吐写成最大容量。”

## 3:20–4:15：监控和失败定位

展示 Grafana 的依赖状态与延迟图，再展示某个原始结果的 `request_id` 及对应脱敏日志。

“`/health` 只说明进程活着，`/ready` 还检查数据库、非空 FAQ 和本地模型。每次请求有编号，日志记录分流原因及分阶段耗时；Prometheus 记录统计，Grafana 展示状态，LangSmith 可查看脱敏阶段追踪。

数据库不可用时可能仍然返回 HTTP 200 的人工提示，因此我另记技术失败，不能只看 HTTP 错误率。此前实际做过数据库停机与恢复，并确认 14 条 FAQ 的内容和向量摘要一致。面板里不放问题、单号和请求编号作标签，避免高基数和隐私暴露。”

不在五分钟内临时停数据库；故障行为展示已有真实记录，需要现场演练时再由面试官明确要求。

## 4:15–5:00：取舍与下一步

“本地小型 BGE 和 pgvector 适合当前 14 条规则的教学数据，部署用 Compose，让 API、数据库和监控配置可复现。没有为了展示框架数量再加 Agent 或 Redis；个人状态查询和通用政策回答已经有明确的不同边界。

当前不足是分流仍基于有限关键词、生成条件可能省略、性能样本较小，并且没有真实业务鉴权或工单执行。下一步优先补条件完整性检查、更多独立题目，再根据实测瓶颈决定优化。我不会把未测的并发上限、商业落地或独立开发能力写进简历。”

## 常见追问：需要能自己回答

- 为什么个人状态不能交给 FAQ RAG 猜测？
- 为什么 Recall@3 为 100% 仍可能答错？
- 为什么 HTTP 200 仍需要记录技术失败？
- 重复问题更快是否就证明有缓存？代码缓存了什么？
- 本轮 P95 的计算、样本数、预热与客户端位置分别是什么？
- 改进由 44/46 到 46/46 的是哪类检查？哪些语义问题仍未解决？

本稿准备完成不代表已通过五分钟口述或独立变式验收。真实演示后再记录时长和追问结果。
