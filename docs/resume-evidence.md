# 简历表述与数字来源

2026-10-03，Codex 辅助整理。按自己能解释和演示的范围选用；如实说明模拟数据与 AI 辅助范围，独立掌握程度尚未验收。

## 可用项目描述

> 在 AI 辅助下开发模拟电商客服 API，分离订单/退款记录查询与 FAQ RAG，使用 FastAPI、本地 BGE 和 pgvector 实现带版本引用的回答及证据不足转人工。修复两处分流缺陷，同一固定 46 题集的自动检查由 44/46 提升至 46/46；30 个 FAQ 问题的检索 Recall@3 为 100%。完成重复与新问法在并发 1、2 下的 80 个完整 RAG 负载样本检查，保存原始响应、耗时、脱敏日志和复算脚本。

自动检查和检索召回不能改写为“客服准确率 100%”。`handoff` 仅提示联系人工，未接入真实工单；没有真实电商用户或营收证据。

## 数字映射

[本轮 raw.json](evidence/20261003-career-run/raw.json)、[历史 baseline.json](evaluation/stage5-baseline.json)及 [复算脚本](../evals/verify_career.py)。

| 文案数字 | 原始位置与计算 | 允许的含义 |
| --- | --- | --- |
| 两处分流缺陷 | 基线失败 ID：`first-person-policy`、`refund-both-ids`；[修复记录](routing-regression.md) | 固定题暴露的两处路由错误已修复并回归 |
| 46 题、44/46 → 46/46 | 前后 `results` 长度及 `dataset_sha256` 相同；统计 `checks` 全真 | 同题集自动检查变化，非盲测或语义准确率 |
| 30 个 FAQ 问题 | 本轮有 `retrieval` 的记录数 | 检索指标分母，含复合题 |
| Recall@3 100% | 前三条检索 ID 与 `case.relevant` 的交集比例逐题平均 | 本轮检索召回，不保证生成条件完整 |
| 并发 1、2 | `benchmarks[].concurrency`，线程池最大线程数 | 本机短时闭环负载，非用户数或容量上限 |
| 80 个负载样本 | 四组 `samples` 各 20 个，共 80 | 路由/人工标志/引用检查全部通过，非全文语义评分 |

四组 P50/P95 与请求/秒见 [实测报告](career-evidence-report.md)。不要单摘最快一组宣称系统容量，须保留小样本、热模型及容器回环条件。

暂不写：生产准确率、缓存加速、最大容量、真实用户、可用率、费用节省、长期 SLA。历史条件省略和本轮冗余补充仍需解释；独立编码及五分钟讲解尚未验收。
