## 运行

先保证 Docker Desktop 正常运行、Compose API 与数据库已启动、`/ready` 返回 200。在项目根目录 PowerShell 执行：

```powershell
./evals/run.ps1 -OutputName stage5-new-run
```

每个固定题只请求一次，不自动重试。性能部分分别测试模拟订单查询（每个并发级别 60 次）和完整 RAG（每级 6 次），并发为 1、2，每组另有 1 次预热。最多 48 次生成调用：固定集最多 34 次，性能含预热 14 次。当前路由可能让部分题不进入生成，因此实际次数可更少。使用已有 DeepSeek 服务，可能产生 API 费用；不会创建新付费服务。

## 指标含义

- 检索：仅统计有明确 FAQ 相关规则的 30 题。Hit@1/3 表示前 1/3 条是否包含任一相关规则；Recall@3 是覆盖相关规则的比例；MRR 是首个相关结果排名倒数的平均值。多规则问题不能以命中一个规则冒充全部覆盖。
- 自动验收：HTTP、四字段响应结构、预期路由、人工标志、必要引用规则。自动通过不等于语义正确，也不证明所有引用都支持答案。
- 语义复核：按 `cases.py` 的 rubric 查看实际答案，核对条件、例外、事实及越权承诺；属于助手辅助复核，非独立人工标注或盲测。
- 业务成功：性能样本必须 HTTP 200 且返回预期路由且不需要人工；HTTP 200 的降级转人工不会算成功。
- 延迟：客户端墙钟时间，预热排除，包含失败样本；P50/P95 用 nearest-rank。完整 RAG 每组仅 6 个样本，P95 等于最大值，仅作初步观测。
- 吞吐：总完成数/墙钟秒数；另报业务成功数/墙钟秒数。

测试客户端在 API 容器内通过 loopback 请求服务，与宿主机或远程真实用户路径不同。串行固定集后再运行性能测试，模型已预热；后台就绪检查、追踪导出和监控仍运行。结果受 CPU、网络和外部生成服务波动影响，不是最大容量或生产 SLA。

评估不修改业务代码、FAQ 或索引；前后比较每条规则的版本、内容和向量摘要。输出保存模拟问答、request_id 和耗时，禁止把环境密钥加入结果。原始结果供回归比较，不得删除失败题后重新计算成功率。业务修复后应另存新结果，并增加未用于调参的测试问法。
